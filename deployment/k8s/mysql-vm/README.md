# MySQL via OpenShift Virtualization

Deploys the Brix Pizza MySQL database inside a **VirtualMachine** managed by OpenShift Virtualization (KubeVirt) instead of a container StatefulSet. The VM runs CentOS Stream 9, installs MySQL 8.0 on first boot via cloud-init, and exposes port 3306 through a standard Kubernetes Service — so the application connects to it exactly as it would to the container-based deployment.

## Files

| File | Kind | Purpose |
| ---- | ---- | ------- |
| `01-namespace.yaml` | `Namespace` | Creates the `brix` namespace |
| `02-secrets.yaml` | `Secret` | `mysql-secrets` — credentials and connection string read by the brix app |
| `03-virtualmachine.yaml` | `VirtualMachine` | VM definition with inline cloud-init that installs and configures MySQL |
| `04-service.yaml` | `Service` | Exposes port 3306 from the VM as `mysql-service` in the `brix` namespace |

## Prerequisites

1. **OpenShift Virtualization operator** installed on the cluster.
2. **CentOS Stream 9 golden image** available (imported automatically by OCP-Virt):

   ```bash
   oc get datasource centos-stream9 -n openshift-virtualization-os-images
   ```

3. If the StatefulSet-based MySQL is still running in the same namespace, remove its conflicting Service before deploying:

   ```bash
   oc delete svc mysql-service -n brix
   ```

   > Note: the mysql directory and the mysql-vm directory should not both be applied. Pick the deployment pattern first and choose one of the two.

## Deploy

```bash
oc apply -f deployment/k8s/mysql-vm/
```

Apply order within the directory is handled by the numeric filename prefix.

## Verify

Wait for the DataVolume to finish importing the OS disk (can take a few minutes):

```bash
oc get datavolume -n brix -w
```

Check that the VM is running:

```bash
oc get vm,vmi -n brix
```

Watch cloud-init progress inside the VM (MySQL install and init takes 2–5 minutes on first boot):

```bash
virtctl console mysql-vm -n brix
```

Once the VM is ready, confirm MySQL is reachable from inside the cluster:

```bash
oc run mysql-check --rm -it --image=mysql:8.0 --restart=Never -n brix -- \
  mysql -h mysql-service -u brix_user -pdemo-brix-pass-CHANGE-ME brix_pizza -e "SELECT 1;"
```

## How It Works

```text
Application Pod
     │  DATABASE_URL → mysql-service.brix.svc.cluster.local:3306
     ▼
 mysql-service (ClusterIP)
     │  selector: vm.kubevirt.io/name=mysql-vm
     ▼
 virt-launcher Pod  ←── KubeVirt masquerade NAT
     │
     ▼
 VirtualMachine (mysql-vm)
     └── mysqld listening on 0.0.0.0:3306
```

KubeVirt labels the `virt-launcher` pod with `vm.kubevirt.io/name: mysql-vm`, which the Service uses as its selector. The VM's interface declares port 3306 explicitly so KubeVirt's masquerade NAT forwards inbound traffic into the VM.

## Customization

**Use RHEL 9 instead of CentOS Stream 9** — edit `03-virtualmachine.yaml` and change the DataSource name:

```yaml
sourceRef:
  kind: DataSource
  name: rhel9        # requires a RHEL entitlement on the cluster
  namespace: openshift
```

**Change storage class** — by default the cluster's default StorageClass is used. To pin a specific class, add a `storageClassName` field under `storage` in `03-virtualmachine.yaml`:

```yaml
storage:
  storageClassName: ocs-storagecluster-ceph-rbd
```

Check available classes with `oc get sc`.

**Production credentials** — replace the demo passwords in `03-virtualmachine.yaml` (the `userData` cloud-init block) and `02-secrets.yaml` with values generated by:

```bash
openssl rand -base64 32
```

**Resize the VM** — edit the `cpu` and `memory.guest` fields in `03-virtualmachine.yaml`. The VM must be stopped and restarted for CPU/memory changes to take effect:

```bash
virtctl stop mysql-vm -n brix
# (after editing the manifest)
oc apply -f deployment/k8s/mysql-vm/03-virtualmachine.yaml
virtctl start mysql-vm -n brix
```

## Tear Down

```bash
oc delete -f deployment/k8s/mysql-vm/
```

This removes the VirtualMachine, its DataVolume (and the underlying PVC), and the Service. MySQL data stored on the PVC will be deleted.
